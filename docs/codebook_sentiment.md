# Разметка тональности отзывов

Версия 1.2

| Метка | Когда ставить |
|---|---|
| 0 – отрицательная | Автор недоволен, описывает недостаток, поломку или не рекомендует продукт |
| 1 – положительная | Автор доволен, хвалит продукт или рекомендует его |
| Пропустить | Нет оценки, не хватает контекста или положительная и отрицательная оценки равнозначны |

> "Пропустить" – решение об исключении объекта, а не третий класс модели.

## Правила

1. Читать предложение целиком.
2. Описание дефекта считается отрицательной оценкой даже без слов *bad* или *hate*. Простое описание функции без оценки пропускается.
3. Если автор называет плюсы и минусы, использовать явно выраженный общий вывод. Если его нет, пропустить. Слово *but* само по себе не определяет ответ.
4. Сарказм учитывать, когда смысл понятен из предложения. При двух равноправных прочтениях пропустить.
5. Не исправлять текст и не дополнять его придуманным контекстом. Если предложение плохо выделено, пропустить с пояснением.

> В конце выгрузить полный JSON с метками и lead_time.
_____

Учебные примеры ниже придуманы для инструкции и не включаются в собранные данные.

| Пример | Решение |
|---|---|
| The player works perfectly. | 1 |
| The app crashes every time I open it. | 0 |
| The app has a dark theme. | Пропустить: факт без оценки |
| Great sound, terrible controls. | Пропустить: равнозначные оценки |
| The controls are awkward, but I still recommend this player. | 1: явный итог |

## Единица разметки и порядок работы

Первоначальные ответы два аннотатора дают независимо, без просмотра ответов друг друга. Для сохранённой партии initial используется исходный экспорт, исправления хранятся отдельно в fixed. При обсуждении спорного случая применяется правило инструкции; исходный ответ не перезаписывается в архиве. Отмена задачи в Label Studio — Skip, не новый класс. Skip хотя бы одного участника исключает объект из итогового обучения; отсутствующие причины не придумываются задним числом.

Версия 1.2 уточняет обработку пропусков, сопоставление экспортов и производные обучающие данные. Наличие версии в каждом исходном JSON проверяется отдельно; отсутствующая версия не восстанавливается как факт.

Один объект — одно представленное предложение/отзыв. Два аннотатора размечают одинаковые object_id. Для итоговой добавки требуются две принятые совпавшие метки. Если в fixed осталось расхождение, объект получает review_required и не включается автоматически. Skip не заменяется меткой другого участника.

При проверке разногласий в initial рассматривались sent_001, sent_004, sent_006; corrected fixed хранится отдельно. Согласие оценивается Cohen’s κ до и после исправлений с явным числом исключённых Skip. Подробности — в README аннотаций.
